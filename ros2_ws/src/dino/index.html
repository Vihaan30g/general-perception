Grounding DINO ROS 2 Package: Text-Prompted Detection in Isaac Sim

A ROS 2 package that runs the Grounding DINO model on a live simulated camera. You type what you want to find, and the objects are located in the running simulation. A new prompt takes effect immediately, without restarting anything.

1. Overview

Most object detectors can only find the fixed list of categories they were trained on. Grounding DINO is different: it takes a sentence-like text prompt, such as "yellow mug . red bottle .", and finds whatever that text describes in the image. This package wraps it as a ROS 2 node so that it can be used on the camera of a running NVIDIA Isaac Sim scene.

It is the first stage of a perception pipeline (Grounding DINO, then SAM, then pose) and was built as a practice project while learning Isaac Sim and ROS 2.

Detection, not segmentation. Grounding DINO returns bounding boxes with a label and a confidence score. Pixel-accurate masks come from the next stage, the sam package, which takes these boxes as its prompts.

3. What is Grounding DINO?

Grounding DINO is an open-vocabulary (open-set) object detector. "Open-vocabulary" means the list of things it can find is not fixed in advance: any object you can describe in words is a valid target. "Grounding" means linking words to image regions, so each phrase in the prompt is tied to the boxes that match it.

The name comes from combining two ideas:

  • DINO here is the detection architecture DETR with Improved deNoising anchOr boxes, a transformer-based object detector. It is not the self-supervised DINO / DINOv2 image-feature models from Meta, which share the name but do something different.
  • Grounded pre-training teaches the model to align image regions with text, which is what lets it follow a free-form prompt.

This package uses the small IDEA-Research/grounding-dino-tiny checkpoint from Hugging Face, loaded through the transformers library. It runs on a GPU if one is available and falls back to the CPU otherwise.

4. How the model works

In brief, the model reads the image and the text separately, mixes the two, and then predicts boxes that are tied to words:

1Encode image and textAn image backbone extracts visual features and a language model encodes the prompt
2Fuse the twoCross-attention layers let image features and text features inform each other
3Pick the best starting pointsLanguage-guided query selection chooses the image locations most related to the text
4Decode boxesA cross-modality decoder refines each query into a box and scores it against the words
5FilterKeep boxes above the box threshold, and name them using the words above the text threshold

Two thresholds control the filtering. This package uses 0.35 for the box confidence and 0.25 for the text match. Raising them gives fewer but more certain detections, and lowering them finds more objects at the cost of false positives.

5. Model inputs and outputs

Inputs

  • An RGB image. Here, one frame from the simulated camera, as an H×W×3 array.
  • A text prompt. The objects to find, as lowercase phrases that each end with . , for example yellow mug . red bottle . green table .

Outputs

  • Bounding boxes as pixel corners [x1, y1, x2, y2].
  • A confidence score for each box.
  • A text label for each box, taken from the prompt.

With an empty prompt the engine returns no detections at all, which is the starting state of the package.

ProgramRole
prompt_manager_node.pyA long-running node that remembers the current prompt. It listens on /dino/prompt_cmd and republishes every change on /dino/active_prompt, using transient-local durability (a "latched" topic). Any node that starts later, even after the prompt was set, immediately receives the last prompt.
set_prompt.pyA one-shot command-line tool, not a persistent node. It publishes one prompt string to /dino/prompt_cmd and exits.
grounding_dino_node.pyThe detector. It receives camera frames and the active prompt, runs Grounding DINO, shows the annotated result in a window and publishes the detections.
dino/dino_engine.pyThe DinoEngine class that wraps the model: it loads the processor and weights, and its infer(image, prompt) returns the list of detections. It does not depend on ROS, so it can be reused or tested on its own.

Inside the detector node

  • Frames are never queued. The camera is faster than the model, so the ROS callback only stores the newest frame, overwriting older ones ("latest frame wins"). The model always works on the freshest image instead of falling further behind.
  • Inference runs in a background thread, so the heavy model call never blocks ROS message handling.
  • The window runs on the main thread. An OpenCV window titled "Grounding DINO" shows each frame with a green box and a "label score" tag per detection. Press q to quit.
  • Camera QoS is matched to the simulator: best-effort with a queue of one, as Isaac Sim's camera bridge typically publishes.
  • An empty prompt means no boxes. Until a prompt is set, the node draws and publishes nothing.

What gets published

Detections go out on /dino/detections as a JSON string. The image timestamp and frame ID are copied into it, so the next stage can find the exact camera frame each result belongs to, even though the model runs slower than the camera.

{
  "header": { "stamp_sec": 1234, "stamp_nanosec": 567890000, "frame_id": "zedx1_link" },
  "prompt": "yellow mug . red bottle .",
  "detections": [
    { "label": "yellow mug", "score": 0.61, "box_xyxy": [412.0, 230.5, 498.2, 330.9] }
  ]
}

The values above are illustrative; the field names are those used by the node.

7. Changing the prompt without restarting

The demo's key feature comes directly from the design. The model is loaded once, when the detector node starts, and stays in memory. The prompt is not baked into the code or a launch file: it is just a string travelling over a topic.

  1. You run set_prompt.py with a new string of objects.
  2. It publishes the string once and exits.
  3. The prompt manager stores it and republishes it as the active prompt.
  4. The detector node updates its prompt under a lock, and the very next frame is processed with the new prompt.

Nothing is reloaded and the simulation is never stopped. Only the small command is run again.

8. Running it

Requirements: ROS 2 with rclpy, sensor_msgs, std_msgs and cv_bridge; Python packages torch, transformers, Pillow, opencv-python and numpy; and an Isaac Sim scene whose camera publishes images on /zedx1/rgb through the ROS 2 bridge. A GPU is recommended. The model weights are downloaded from Hugging Face the first time the node starts.

# build the package from the ROS 2 workspace
cd ros2_ws
colcon build --packages-select dino
source install/setup.bash

Then use three terminals, each with the workspace sourced, and the Isaac Sim scene playing:

# terminal 1: keeps the active prompt
ros2 run dino prompt_manager_node.py

# terminal 2: loads the model and starts detecting
ros2 run dino grounding_dino_node.py

# terminal 3: set (and later change) what to look for
ros2 run dino set_prompt.py "yellow mug . red bottle . green table ."

To look for something else, run the last command again with a new string. Put all objects in one string, in lowercase, each phrase ending with . . The .py suffix after the program name is required for these commands. Specific, descriptive phrases ("red bottle" rather than "bottle") usually work best.

  • Where it fits. This is stage one of a Grounding DINO, SAM and pose pipeline. The sam package already listens to /dino/detections and turns each box into a mask.
  • Speed. Detections update at the speed of the model, not the camera, because of the latest-frame-wins design. A GPU makes a large difference.
  • A learning project. It was written to practise ROS 2 and Isaac Sim integration, so the messages are plain JSON strings rather than custom message types.
